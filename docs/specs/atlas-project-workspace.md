# Atlas project workspace

Opening Atlas presents a public landing page. Users can explore the explicitly labelled Aegra example or create an account with email and password. A signed-in account owns its repository projects. New projects accept public GitHub repository URLs. Registering the same repository twice opens the existing project. A server job builds a static code graph using the existing exporter, records the exact revision, and persists the result. Projects, results and account sessions survive a service restart. Interrupted work is recoverable. Read-only saved issue data can be displayed when present. A graph-only scan describes its review coverage accurately.

The workspace has one project selector at upper left, a new-project action, a slim row of four views, a left control area and a large canvas or list. The initial project view is 3D. Its controls, 2D inspection, routes and recorded issues refer to the same project and revision. Selecting a route opens its 2D trace. Project changes discard stale responses. An empty, failed, missing or unauthorized project never substitutes sample data. Existing explicit sample links and their 2D/3D choices remain usable. Browser history and reloading identify the project and view.

## Delivery contracts

- The local product API is a separate FastAPI app, `scan_api.workspace_server:app`, reached through the existing same-origin Vite proxy. It exposes only workspace APIs, not the old unscoped list or scan routes. SQLite owns identity, opaque hashed sessions and owner/repository mapping. Account-scoped request and artifact reads return 401 without a session, 404 for another account's project. Mutations check origin and JSON content. Product jobs use anonymous public GitHub access and static graph generation, with no model review. Existing standalone scan tooling and historical local data remain separate.
- API paths below omit the browser's `/api` prefix. `GET /session` → `{user: {id,email} | null}`; `POST /auth/register` and `POST /auth/login` take `{email,password}` and return `{user}` with a session cookie. `POST /auth/logout` ends the session. `GET /projects` → `{projects: Project[]}`; `POST /projects` takes `{repositoryUrl}` → `{project: Project}`; `GET /projects/{id}` and `POST /projects/{id}/retry` → `{project: Project}`. Project is `{id,repositoryUrl,scan: ScanSummary}` where ScanSummary matches src/api.ts. `GET /projects/{id}/graph` returns the persisted graph document; `GET /projects/{id}/files` returns the existing FileManifest shape. Errors carry `{error: string}`. A worker or public-access failure has a retryable state or a clear preflight error. The account is per local installation.
- The report component exports `ProjectReport({graph,source,manifest,view,onViewChange})` from src/ProjectReport.tsx with views `'3d'|'2d'|'routes'|'issues'`. It accepts the existing AtlasGraph and ScanSource types. Api sources accept an optional `projectId` to construct protected graph download URLs. The surrounding app owns the top selector/tabs, data fetch, user interaction and project routing. The report owns the left controls, list/detail panels, and viewport-specific navigation. Both use the repository's existing typography and colors.

## Implementation and acceptance

1. Implement the workspace API and static worker in an isolated checkout. Verify using the Python test suite, separate accounts, canonical duplicate URLs, rejected inputs, persistence, failure/retry, artifact availability and two source identities.
2. Implement embedded report views in a separate checkout. Keep the cinematic graph interactive and bounded by its host. Reuse the same graph model for all views. The route and issue lists must handle zero and nonzero records truthfully.
3. Implement the landing, authentication and project shell in the primary checkout. Assemble integrations and update local run instructions. Keep the sample explicit and allow opening another project even from a failed job.
4. Independently review the integrated change and verify registration, login, creation, polling, project switching, navigation, and public sample behavior in the local browser. Compare counts/identities against stored JSON from two real public repositories. Check desktop and compact layouts and leave the local product running.

Local delivery only. The real worker requires the installed Joern and Java toolchain and public GitHub access.
